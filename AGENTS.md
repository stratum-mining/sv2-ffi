# AGENTS.md

This file provides guidance for agents working on this repository. It is committed to the repository, which means agents from all contributors follow the same conventions.

Contributors are free to add their own custom guidance for their agents via `AGENTS_CUSTOM.md`, which is NOT committed to the repository.

Aside from guidelines on these files, also always take into consideration `CONTRIBUTING.md` and `README.md`.

Pay special attention to `CONTRIBUTING.md` when crafting git commits.

## What this repository is

C bindings to the Stratum V2 Reference Implementation: a C API over the crates published from [`stratum`](https://github.com/stratum-mining/stratum), with its header generated by cbindgen. Bindings for the languages UniFFI supports live in [`sv2-uniffi`](https://github.com/stratum-mining/sv2-uniffi).

## Bindings, not an implementation

Every protocol decision is made by a `stratum` crate: the Noise handshake and the encrypted transport by `codec_sv2`, message dispatch and encoding by `parsers_sv2` and the subprotocol message crates, channel state and share validation by `channels_sv2`. Code in this repository converts between C records and the crates' types, maps errors to C status codes and owns nothing else. Whenever a change would reimplement something a crate already does, or would make a protocol decision the crate does not, stop and say so: the fix belongs in `stratum`, and this repository follows it with the next release.

Expose the crates' public API, not their plumbing. `binary_sv2`, `buffer_sv2`, `framing_sv2` and `handlers_sv2` are not part of the C API beyond what a caller strictly needs to read and write frames on its own socket.

## Cross-repo development

This repository depends on the `stratum` crates as released on crates.io, never on a git revision. A change this repository needs in a crate goes to `stratum` first, as its own issue and PR there, and reaches here with the next release. Whenever a bump of the `stratum` crates changes a message struct or a channel API, the bindings and the committed header change in the same PR as the bump.

## The committed header

The C header is generated by cbindgen from the Rust sources and committed, so a C program can build without a Rust toolchain. Whenever a change touches an exported function, record or constant, regenerate the header with the cbindgen version CI uses and commit it in the same commit as the change. The header is the API: a renamed field or a changed constant value is a breaking change, even when the wire format is untouched.

## Memory and panics at the boundary

The C side owns every buffer it passes and sees no Rust lifetime: an encoder writes into a caller buffer of a given capacity, and a decoded record points into the frame its session keeps, valid until that session's next decode or its free. The only Rust allocations a caller holds are the objects of `_new()` functions, released by their `_free()`. No panic crosses the boundary: every exported function catches it and reports an error code. Whenever adding or changing an exported function, keep these rules, and cover the error paths from C, under the sanitizers, not only from Rust.

## Code comments and attributes

A comment block above an item describes the item that follows it, so inserting a new item directly below one steals it: the new item inherits a description written for something else, and the item it was written for is left with nothing. Attributes bind the same way: an item placed between an attribute and its item takes the attribute over. Whenever adding an item to an existing file, look at what sits immediately above the insertion point, comments and attribute lines both, and whenever lifting a helper into a file from somewhere else, look again once it has landed. Nothing fails to compile and no lint catches it; one unbroken run of comment lines carrying two separate summaries is the sign that it happened.

## Bug patching

Whenever patching bugs, always keep me informed about potential side-effect implications on non-trivial aspects of the project functionality (e.g.: memory safety at the C boundary, behaviour of C programs already built against the header, new bugs or vulnerabilities).

Whenever writing documentation around bug fixes, always write the comment assuming the reader is simply trying to understand the code as is, not the past history of bugs that existed on that code.

## PR reviews

Whenever helping me review PRs, don't restrict the output to an analysis of the PR. Also help me understand the PR progressively across two axis:

- conceptual (taking issues and other related PRs into consideration)
- commit history

While listing findings, for each finding, give me a draft comment and the file/line where it would be appropriate to drop it. Also mention the finding severity, and whether you believe it's a blocker or not. This is deliberately designed to keep human reviewers on the loop, as opposed to blindly copypasting a huge "clanker review" body of text without ever looking into what each finding means.

Judge a PR against the problem and the expected outcome of the issues it closes. Everything else an issue lists is context: a PR that reaches the outcome another way is not a finding, as long as its description explains why. Flag a divergence only when part of the expected outcome is left unsolved, and say which part.

## Drafting issues

SRI repositories try to leverage github subissue clustering. When helping humans draft new github issues, always find for issues that might be either adjacent, correlated, duplicate. Also take into consideration umbrella issues that have already been closed.

You always draft github issues under human supervision. Your role here is to help human SRI contributors reason about the issues being reported, not create github noise.

Describe the problem and the outcome a fix must guarantee, observable from outside the code. Leave out how to fix it, non-binding ideas included: the solution is up to whoever picks up the issue.

A defect in what a crate decides (a share verdict, a handshake failure, a message the crate refuses) is a `stratum` issue, even when it was found through these bindings. File it there and link it from here.

## Ponytail

If the plugin is not already installed into the coding agent harness, make sure to follow [Ponytail](https://ponytail.dev/) rules. But avoid installing it as a plugin, unless explicitly instructed to do so. This is only a repository-wide convention. Also avoid writing comments that reference "ponytail" in a compressed and implicit way, prefer explaining the actual rationale instead.
